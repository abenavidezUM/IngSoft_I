CU0008 - BORRAR MENSAJES PROPIOS
----------------------------

ESPECIFICACIÓN DEL CASO DE USO:
--------------------------------
Descripción: Permite a los usuarios borrar los mensajes que han publicado en su 
             tablón de anuncios.
Actor: Usuario
Precondición: El usuario ha iniciado sesión en el sistema
Frecuencia: Diariamente

FLUJO NORMAL (Especificación → Implementación):
------------------------------------------------

PASO 1 DISEÑO: "El usuario visualiza la pantalla de mensajes propios y selecciona 
                el mensaje que desea borrar"

IMPLEMENTACIÓN:
  - Frontend: MensajesPropiosComponent (mensajes-propios.component.ts)
  - Método: ngOnInit() → cargarMensajes() → obtenerTablon()
  - Endpoint: GET /api/mensajes/tablon
  - Servicio Backend: obtener_tablon() en mensajes_service.py
  
  COHERENCIA: ✅ COMPLETA
  - La interfaz muestra el tablón con mensajes propios + de seguidos
  - Solo mensajes propios tienen botón "Borrar" visible (flag esPropio)
  - Usuario puede identificar y seleccionar sus mensajes

PASO 2 DISEÑO: "El sistema muestra el mensaje seleccionado con la opción para borrarlo"

IMPLEMENTACIÓN:
  - HTML: Botón "Borrar" renderizado solo si mensaje.esPropio === true
  - Código: <button *ngIf="mensaje.esPropio" (click)="borrarMensaje(mensaje.id)">
  
  COHERENCIA: ✅ COMPLETA
  - Botón visible únicamente en mensajes del usuario autenticado
  - Distinción visual (badge "Tu mensaje", borde azul)

PASO 3 DISEÑO: "El usuario selecciona la opción de borrado y confirma los cambios"

IMPLEMENTACIÓN:
  - Frontend: borrarMensaje(mensajeId) en mensajes-propios.component.ts
  - Confirmación: confirm('¿Confirma el borrado de su mensaje?')
  - Llamada API: mensajesService.borrarMensaje(mensajeId)
  - Endpoint: DELETE /api/mensajes/<mensaje_id>
  
  COHERENCIA: ✅ COMPLETA
  - Confirmación explícita del usuario antes de borrar
  - Opción de cancelar (curso alternativo 2.1)

PASO 4 DISEÑO: "El sistema valida el borrado, actualizando el tablón de anuncios"

IMPLEMENTACIÓN Backend:
  - Validación 1: Usuario autenticado (jwt_required)
  - Validación 2: Mensaje existe (borrar_mensaje verifica en BD)
  - Validación 3: Usuario es el autor (comparación autor vs usuario_id)
  - Actualización: db.mensajes.delete_one({'_id': mensaje_oid})
  - Respuestas: 200 (OK), 403 (no es autor), 404 (no existe)

IMPLEMENTACIÓN Frontend:
  - Actualización optimista: Remueve mensaje de la lista local
  - Código: this.mensajes = this.mensajes.filter(m => m.id !== mensajeId)
  - Manejo de errores: Muestra alert si falla
  
  COHERENCIA: ✅ COMPLETA
  - Todas las validaciones de seguridad implementadas
  - Vista se actualiza automáticamente
  - Usuario ve cambios inmediatamente

CURSO ALTERNATIVO 2.1 (Cancelar borrado):
------------------------------------------

DISEÑO: "Usuario cancela → Sistema descarta cambios → Vuelve al tablón sin actualizar"

IMPLEMENTACIÓN:
  - Frontend: if (confirm('¿Confirma...?')) { /* borrar */ }
  - Si usuario cancela, confirm() retorna false
  - No se ejecuta la llamada HTTP
  - Vista permanece sin cambios
  
  COHERENCIA: ✅ COMPLETA

CU0016 - ENVIAR CORREO AUTOMÁTICO DE TENDENCIAS
----------------------------

ESPECIFICACIÓN DEL CASO DE USO:
--------------------------------
Descripción: Enviar a una lista de usuarios un correo con los temas del momento 
             basada en las etiquetas más populares
Actor: Usuario (receptor)
Actor implícito: Sistema (automatizado)
Precondición: El usuario ha iniciado sesión
Frecuencia: Semanal (automático)

FLUJO NORMAL (Especificación → Implementación):
------------------------------------------------

PASO 1 DISEÑO: "El sistema recopila y analiza los mensajes más recientes"

IMPLEMENTACIÓN:
  - Servicio: obtener_tendencias() en tendencias_service.py
  - Agregación MongoDB:
    * Filtra mensajes de últimas N horas
    * Usa $unwind para separar etiquetas
    * Pipeline: find → filter fecha → unwind etiquetas
  - Código relevante:
    fecha_limite = datetime.utcnow() - timedelta(hours=horas)
    mensajes = db.mensajes.find({'fechaDeCreado': {'$gte': fecha_limite}})
  
  COHERENCIA: ✅ COMPLETA
  - Recopilación automática basada en fecha
  - Análisis de todos los mensajes públicos recientes

PASO 2 DISEÑO: "El sistema identifica las etiquetas más utilizadas"

IMPLEMENTACIÓN:
  - Contador de frecuencias: Counter() de collections
  - Iteración sobre todas las etiquetas encontradas
  - Código: counter = Counter([etiqueta for msg in mensajes for etiq in etiquetas])
  
  COHERENCIA: ✅ COMPLETA
  - Identificación automática de etiquetas
  - Conteo de frecuencia de uso

PASO 3 DISEÑO: "El sistema genera la lista de los temas del momento"

IMPLEMENTACIÓN:
  - Ordenamiento: counter.most_common(limit)
  - Formato: Lista de tuplas (etiqueta, frecuencia)
  - Retorno estructurado: [{'etiqueta': '#python', 'frecuencia': 5}, ...]
  
  COHERENCIA: ✅ COMPLETA
  - Top N etiquetas más frecuentes
  - Ordenadas de mayor a menor

PASO 4 DISEÑO: "El Usuario recibe un email con los temas del momento"

IMPLEMENTACIÓN:
  - Generación HTML: generar_contenido_email() en tendencias_service.py
  - Envío SMTP: enviar_email_tendencias() en email_service.py
  - Configuración: Flask-Mail con Gmail SMTP
  - Lista de destinatarios: obtener_usuarios_para_envio()
  - Script standalone: enviar_tendencias.py (para cron/automatización)
  
  COHERENCIA: ✅ COMPLETA
  - Formato HTML profesional con estilos
  - Envío masivo a todos los usuarios con email válido
  - Manejo de errores individuales (no falla todo si uno falla)

CURSO ALTERNATIVO 2.1 (Email no enviado):
------------------------------------------

DISEÑO: "Error en direcciones → Sistema descarta envíos"

IMPLEMENTACIÓN:
  - Validación: validar_configuracion_email() antes de enviar
  - Try-except: Captura errores SMTP por usuario
  - Estadísticas: Cuenta exitosos y fallidos
  - Log de errores: Imprime error pero continúa con siguiente usuario
  
  COHERENCIA: ✅ COMPLETA
  - No interrumpe proceso si un email falla
  - Registra errores para análisis posterior

   - Curso alternativo "cancelar" → confirm() retorna false

PREGUNTA 2: "¿Qué patrones de diseño utilizaste y por qué?"
------------------------------------------------------------

RESPUESTA:

1. PATRÓN REPOSITORY (Implícito en Services):
   - services/mensajes_service.py encapsula acceso a datos
   - Abstrae lógica de MongoDB de las rutas
   - Permite cambiar implementación de BD sin afectar controladores
   - Ejemplo: borrar_mensaje() maneja toda la lógica de persistencia

2. PATRÓN MVC/MVVM (Arquitectura general):
   - Model: models/mensaje.py, models/usuario.py (MongoEngine)
   - View: Components Angular (HTML + CSS)
   - Controller/ViewModel: Components TS + Services
   - Separación clara de responsabilidades

3. PATRÓN FACADE (Services como fachada):
   - tendencias_service.py expone interfaz simple: obtener_tendencias()
   - Oculta complejidad de agregación MongoDB
   - email_service.py abstrae configuración SMTP compleja

4. PATRÓN STRATEGY (Servicios intercambiables):
   - email_service.py puede usar Gmail, SendGrid, etc.
   - Configuración por variables de entorno
   - Fácil cambio de proveedor

5. DEPENDENCY INJECTION (Angular + Flask):
   - Angular: Servicios inyectados en constructores
   - Flask: Blueprints registrados en app.py
   - Facilita testing con mocks

PREGUNTA 3: "¿Cómo aplicaste los principios SOLID?"
----------------------------------------------------

RESPUESTA:

S - SINGLE RESPONSIBILITY PRINCIPLE:
   - mensajes_service.py: Solo lógica de mensajes
   - email_service.py: Solo envío de emails
   - tendencias_service.py: Solo cálculo de tendencias
   - Cada clase/módulo tiene una única razón de cambio

O - OPEN/CLOSED PRINCIPLE:
   - Servicios extendibles sin modificar código existente
   - Nuevos tipos de notificación: Agregar nuevo servicio, no modificar email_service
   - Nuevos métodos de autenticación: Decoradores reutilizables

L - LISKOV SUBSTITUTION PRINCIPLE:
   - Modelos MongoEngine son intercambiables donde se espera Document
   - Servicios pueden mockears e en tests sin romper contratos

I - INTERFACE SEGREGATION PRINCIPLE:
   - Servicios Angular con interfaces específicas (MensajesService, AuthService)
   - No obligan a implementar métodos innecesarios

D - DEPENDENCY INVERSION PRINCIPLE:
   - Dependencia de abstracciones (interfaces) no de implementaciones concretas
   - MongoDB podría cambiarse por PostgreSQL cambiando solo services
   - Flask-Mail podría cambiarse por otro proveedor SMTP

PREGUNTA 4: "¿Cómo garantizas la seguridad de la aplicación?"
--------------------------------------------------------------

RESPUESTA:

AUTENTICACIÓN:

PROTECCIÓN DE CREDENCIALES:
   - Variables sensibles en .env (no en código)

CORS:
   - Flask-CORS configurado

PREGUNTA 6: "¿Qué decisiones de arquitectura tomaste y por qué?"
-----------------------------------------------------------------

RESPUESTA:

1. ARQUITECTURA EN CAPAS:
   
   Capa Presentación (Angular):
   - Components: Lógica de vista
   - Services: Comunicación HTTP
   - Interceptors: Manejo de tokens
   
   RAZÓN: Separación de concerns, testabilidad, mantenibilidad

   Capa Aplicación (Flask):
   - Routes (Controllers): Manejo HTTP
   - Services: Lógica de negocio
   - Utils: Funciones auxiliares
   
   RAZÓN: Facilita cambios sin efecto cascada

   Capa Persistencia (MongoDB):
   - Models (MongoEngine): ODM
   - PyMongo directo: Queries complejas
   
   RAZÓN: Flexibilidad entre abstracción y performance

2. ARQUITECTURA REST:
   - Endpoints semánticos: /api/mensajes, /api/tendencias
   - Verbos HTTP apropiados: GET, POST, DELETE
   - Respuestas JSON estructuradas
   
   RAZÓN: Estándar industry, fácil integración, stateless

3. MICROSERVICIOS SIMULADOS:
   - Backend y Frontend separados
   - Comunicación por HTTP/JSON
   - Puertos diferentes (5001, 4200)
   
   RAZÓN: Escalabilidad, despliegue independiente

4. BASE DE DATOS NoSQL (MongoDB):
   - Esquema flexible
   - Referencias entre documentos (Usuario → Mensaje)
   - Agregaciones para análisis
   
   RAZÓN: Naturaleza del dominio (red social, datos variados)

POSIBLE CRÍTICA: "El envío de emails no es realmente automático"

2. Programación con cron (Linux/Mac) o Task Scheduler (Windows):
   0 9 * * 1 cd /path/backend && python enviar_tendencias.py

El script ES automático, simplemente requiere configuración del scheduler,
que es responsabilidad de deployment, no de desarrollo.

Alternativa implementada: Endpoint POST /api/tendencias/enviar
Permite trigger manual o desde otro sistema automatizado."
